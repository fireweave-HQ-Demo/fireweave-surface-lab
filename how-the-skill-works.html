How surface detection works

This is the rulebook for reading a repository and writing the surface report. Each project folder is judged on its own. The folder name is not evidence.

For this folder: what, if anything, actually runs, and which line proves it?

A surface is a part of the product you would run and watch: a server, a background worker, a website, or a command-line program. A shared library, a test or build script, and an empty placeholder are not surfaces, even when they have a package file or a name that sounds like an app.

Three rules

A yes needs a file and a line. Saying “this runs” is allowed only with the exact line that starts it. Creating the app, exporting a route, or pointing at a config file is not enough. A server has to open a port and stay running. A worker has to enter a loop or wait on a queue. That line has to be one the program reaches: the top of the file, the language’s entry, or a function that entry calls. A brace or /* inside quotes is text. It does not open a block, and it does not hide a later line.
A no needs a record of the search. Saying “nothing runs here” is allowed only when the report lists what was opened and what was searched. “We did not find it” and “we did not look” are different answers. An empty search is rejected.
A line that runs can still be the wrong kind. if __name__ == "__main__": with a listener in that block is a server, and the citation is the listener. func main with r.Run or ListenAndServe inside it is a server, and the citation is that call. The same guard with no listener under it runs and is not a surface. Record the file and line as runs_not_surface. Leave it off the surface list.

If the proof is incomplete, the folder goes to review. It is not forced into a yes or a no.

The nine steps

The steps run in this order for every project folder. A later step cannot skip an earlier one. A package file is a lead. It is not the proof.

  1. List the folder

    Find each project folder: a folder with its own package file, or a folder of real source code that has none. List the files, three folders deep. Skip installed dependencies and build output, including node_modules, dist, .next, virtualenvs, and vendor. Write down every folder that was skipped.

    Done when the folder, its languages, its files, and its skips are recorded.

  2. Read the package file, and stop there

    Write down the scripts, the dependencies, and the description. Words such as “later phase” or “coming soon” are notes. They are not a reason to drop the folder.

    Done when the scripts and dependencies are written down, and no decision has been made.

  3. Write the expectation, for and against

    Write what you expect this folder to be, and why. Name the evidence for that expectation and the evidence against it. In a repository split into apps and packages, read the conventions reference first.

    If the apps folders declare a start, serve, dev, or worker command, or sit beside a program file, and the packages folders do not, the expectation is: apps run, packages are libraries. Write one line of evidence per folder, and list the folders that break the pattern. A folder that breaks it is investigated in full. The pattern does not shorten the search and it does not drop the folder.

    A filename is not the expectation. A description is not the expectation. A folder of real source with no package file is not covered by the apps-and-packages pattern. Judge it from the code.

    Done when the expectation, the evidence for it, the evidence against it, and any exception are written down. No file has been accepted or rejected yet.

  4. Write the search plan before judging

    For each kind, list the searches you will run. Do this before any file is judged.

    • A server: the listener column for that language. JavaScript: serve(, listen(, Deno.serve(. Python: uvicorn.run, server.run(, execute_from_command_line. Go: ListenAndServe, .Run(, .Start(. Rust: HttpServer::new, Server::bind, axum::serve. Java: SpringApplication.run, port(8080).
    • A worker: while True, asyncio.run of a queue, worker.run(, a scheduled job.
    • A website: a page with its assets, or a site config.
    • A command: argument parsing, then exit.
    • A library: exports only, and no line that runs.

    The plan names the file patterns, the text searches, and the package file that will be opened.

    Done when that plan is written down, and no line has been accepted as proof.

  5. Follow what the project declares

    Open each start, serve, dev, and worker script, and the last command a container image runs. If it names a file in the folder, open that file and find the line that starts the program. If the file is missing, record that and keep going. A test, lint, or build script is not a surface. A container command that only starts a stock process, such as nginx, did not resolve to a program in this folder.

    For a few frameworks the script line itself is the server: next start, next dev, gunicorn, and Django runserver. The config file and a route function are not. Every other start command is a lead. Follow it to a listener in the source.

    Done when every declared script has been followed to a line, or recorded as unresolved.

  6. Search the code itself

    Also read the source in the folder. A program with no start script can still be a surface. Record every file that was opened. Do not decide from the filename. worker.py and server.py are hints only.

    Done when the search notes name the files opened and the searches run.

  7. Name it from the line, not the folder

    The line decides the kind, and the program has to reach that line: the top of the file, the language’s entry (if __name__, func main, fn main, main), or a function that entry calls. A folder named browser-runner whose code calls serve_forever() is a server, because that call opens a port and does not return. A folder named worker that only exports functions is a library. One folder can contain two surfaces, such as a server and a worker side by side.

    When the listener sits inside the entry, cite the listener. server.run() or execute_from_command_line(...) under if __name__ is a server. r.Run or ListenAndServe inside func main is a server. The guard line is the entry. The call under it is the proof. A guard or func main with no listener under it is runs_not_surface.

    Done when each yes points at one line, that line matches the kind, and the program reaches it.

  8. Say how this could be wrong, then go check

    Write the specific fact that would make the answer wrong. Then go check that fact. The check has to be an action: open a file, run a search, or read a line. Repeating the expectation is not a check.

    • You said library. Wrong if something runs it, or a container command starts it. Open that command.
    • You said nothing runs. Wrong if a container command or a script was never opened. Open it.
    • You said server. Wrong if the listener sits inside a function nothing calls, or the same program also waits on a queue. Read that line.

    After the check, a second pass re-reads the cited line and does not trust the write-up. The file has to exist. The line has to exist. The line itself has to be the start for the kind you named, in that language. A constructor on the line above does not count, even when the real start is the next line. The program has to reach the line. Quotes are not code: a { or /* inside a string does not open a block and does not hide a later listener. If you said a script led you there, that script is followed again and the line has to match. A “nothing runs” answer needs a non-empty search: at least one attempt to follow a script, one sweep of the code, and every file you opened. A “this runs” answer cannot be a library or a test script. A guard that runs and contains no listener stays runs_not_surface, with the file and line, and is not a surface. Any failed check moves the folder to review. Nothing is upgraded.

    Done when the challenge names a concrete check, that check was done, and the second pass has accepted the line or moved the folder to review.

  9. Write the report

    Surfaces are sorted with the strongest proof first. High means a declared script led to the line and the checker agreed. Medium means the line was found by reading the code, with no script pointing at it. Review means the proof was not enough to say yes or no. A folder whose only executing line is a guard with no listener stays off the list. The report keeps that file and line.

    Done when every running program is listed with its line, and every other folder is under not selected or review. One folder can list more than one program.

Example

apps/api declares dev: tsx src/server.ts. The dependency list includes Hono. This is one folder, walked through the steps that decide the line.

Expectation. A server, because the dev script names a source file. For: the script is tsx src/server.ts, not a test runner. Against: the file might only construct the app and never start it.

Search plan, before judging. In that file, search for serve( and listen(. Do not accept new Hono(). The package file also has a worker script, so search src/worker.ts separately for worker.run().

Follow the script. src/server.ts exists. Line 26 is new Hono(). That line creates the app and does not open a port. Line 30 is a route, "/api/auth/*". The /* is inside a string, so it does not start a comment, and the rest of the file is still code. Line 275 is serve({ fetch: app.fetch, port: env.port }). That is the line.

How this could be wrong. The dev script might point at a test runner, or serve() might sit inside a function nothing calls. Check: open package.json and read scripts.dev. It is tsx src/server.ts. Open src/server.ts at line 275. serve() is at the top level, not inside an unused function.

The written result. Every field is required. An empty one means go back, or send the folder to review.

{
  "unit": "apps/api",
  "claim": "runs",
  "category": "service",
  "entrypoint": {
    "file": "apps/api/src/server.ts",
    "line": 275,
    "snippet": "serve({ fetch: app.fetch, port: env.port }, () => {"
  },
  "evidence_kind": "resolved_declaration",
  "searched": {
    "globs": ["apps/api/**/*.ts"],
    "greps": ["resolve:dev: tsx src/server.ts", "serve\\(", "\\.listen\\("],
    "files_opened": ["apps/api/package.json", "apps/api/src/server.ts"]
  },
  "counter_hypothesis": "wrong if scripts.dev points at a test runner, or if serve() is inside a function nothing calls",
  "counter_checked": "opened apps/api/package.json scripts.dev → tsx src/server.ts; opened apps/api/src/server.ts:275 → serve() at top level",
  "coverage": {
    "inspected": 11,
    "skipped": [{ "path": "node_modules", "reason": "excluded" }],
    "uncertain": []
  },
  "confidence": "high"
}

Citing line 26, new Hono(), is rejected. The second pass re-reads that line, sees a constructor, and sends the answer to review. Treating "/api/auth/*" as a comment and then reporting that nothing runs is the same failure: the search stopped in the middle of a string.

The same citation rule in Python and Go. manage.py reaches execute_from_command_line(sys.argv) from if __name__ == "__main__". The line is that call, and the kind is a server, because the call starts runserver. server.run() under the same guard is a server. r.Run inside func main is a server. Citing the guard and leaving out the call is rejected. A guard whose block has no listener is runs_not_surface: the file and line are kept, and the folder is not a surface. A { inside a Go raw string is text. It does not open a block, and ListenAndServe after it still counts.
